1. Visión General y Arquitectura

Esta API proporciona los servicios backend requeridos para nutrir aplicaciones móviles y clientes web que requieran orientación espacial, directorios informativos, búsqueda predictiva y geolocalización asistida en entornos delimitados.

1.1. Filosofía "Offline-First"

En campus universitarios extensos o cascos históricos, la conectividad celular o Wi-Fi puede ser inestable o inaccesible en sótanos, zonas arboladas o edificios antiguos de muros gruesos. Por ello, la arquitectura contempla un Endpoint de Sincronización Consolidada (/api/v1/sincronizar) diseñado para descargar en un único paquete JSON todo el inventario de datos activos (inmuebles, clasificaciones, palabras clave y polígonos/accesos GPS) e guardarlo en el almacenamiento local que el desarrollador elija (por ejemplo SQLite, Room / CoreData o almacenamiento clave-valor; ver sección 6). La aplicación puede funcionar con autonomía del 100% sin conexión a internet.

1.2. Adaptabilidad y Replicabilidad (Universidades y Centros Históricos)

El modelo de datos fue diseñado con un alto grado de abstracción que permite reutilizar el sistema en diversos contextos sin modificar la lógica interna:

2. Convenciones Generales de la API

2.1. Encabezados HTTP (Headers)

Encabezados Obligatorios en Solicitudes (Request Headers):

Toda solicitud efectuada a la API debe incluir los siguientes encabezados:

Accept: application/json
Content-Type: application/json

Acceso Público (Sin Autenticación):

La versión actual del API es de consulta libre e institucional, diseñada para la práctica de aula. Todos los endpoints son de lectura pública: no requieren login, tokens Bearer ni encabezado Authorization. Las peticiones son simples y directas.

Encabezados Opcionales en Solicitudes (Request Headers):

  • X-Device-Id (string, opcional pero altamente recomendado en las prácticas de clase): Identificador único (UUID) del dispositivo móvil o cliente. Permite aislar el conteo de cuota de peticiones por dispositivo, de modo que los compañeros de aula que comparten la misma red Wi-Fi (misma IP pública / NAT) no compartan cuota entre sí. Si no se envía esta cabecera, la cuota se computa únicamente por la dirección IP del cliente (fallback).

Encabezados de Control en Respuestas (Response Headers automáticos de Laravel):

En todas las peticiones a la API v1, el servidor inyecta encabezados HTTP estandarizados informando el estado de la cuota:

  • X-RateLimit-Limit: Cantidad máxima de peticiones permitidas por ventana de tiempo (100 req/min por dispositivo, cuota unificada para todos los endpoints).
  • X-RateLimit-Remaining: Cantidad de peticiones restantes disponibles en la ventana actual de un minuto.
  • Retry-After: Cantidad de segundos de espera requeridos antes de volver a solicitar en caso de recibir un bloqueo HTTP 429.

2.2. Formato Estándar y Unificado de Respuestas JSON (Sección 7.1)

Todos los controladores retornan una envoltura estandarizada con código HTTP acorde:

A. Respuesta para Colecciones o Listas (200 OK)

{
  "success": true,
  "message": "Mensaje descriptivo de la operación realizada",
  "data": [
    { ... },
    { ... }
  ]
}

B. Respuesta para Registros Individuales u Objetos (200 OK)

{
  "success": true,
  "message": "Mensaje descriptivo de la operación realizada",
  "data": {
    "campo": "valor"
  }
}

C. Respuesta en Caso de Error o Validación (400, 404, 422, 500)

{
  "success": false,
  "message": "Descripción comprensible del error ocurrido",
  "errors": null
}

(En caso de error de validación 422 Unprocessable Entity, el campo errors contiene un mapa de validaciones por atributo).

D. Respuesta en Caso de Límite de Cuota Excedido (429 Too Many Requests)

{
  "success": false,
  "data": null,
  "message": "Límite de peticiones excedido (100 por minuto). Intente nuevamente en un minuto."
}

3.1. Sincronización Offline

↑ Volver al índice de endpoints

Descarga el catálogo consolidado completo de todos los inmuebles activos junto con su categoría funcional anidada, su listado plano de etiquetas indexadas y su totalidad de coordenadas georreferenciadas (entradas y vértices perimetrales).

  • Método: GET
  • Ruta: /api/v1/sincronizar
  • Autenticación: Pública (sin login ni tokens)
  • Protección de Tasa (Rate Limiting): throttle:api-movil (Máximo 100 peticiones/minuto por dispositivo: X-Device-Id + IP, o solo IP si no se envía el header)
  • Parámetros de Entrada: Ninguno

Códigos de Respuesta:

  • 200 OK: Operación exitosa.
  • 429 Too Many Requests: Límite de peticiones excedido (más de 100 peticiones por minuto desde el mismo dispositivo).

Ejemplo de Petición (cURL):

curl -X GET "http://localhost/api/v1/sincronizar" \
     -H "Accept: application/json" \
     -H "X-Device-Id: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"

Descripción de Campos Raíz:

  3. Si el valor del servidor es posterior al local, persiste/sobrescribe los datos locales (SQLite, SharedPreferences o DataStore) y actualiza campus_ultima_sincronizacion.
  4. Si no es posterior, conserva los datos locales sin modificarlos.

Parámetro Tipo Requerido Descripción Ejemplo

3.4. Accesos GPS y Coordenadas de un Edificio

↑ Volver al índice de endpoints

Recupera los puntos georreferenciados asociados a un inmueble. Permite discriminar entre accesos transitables y vértices perimetrales para alimentar la brújula y los motores de guiado.

  • Método: GET
  • Ruta: /api/v1/edificios/{id}/accesos
  • Autenticación: Pública (sin login ni tokens)
  • Protección de Tasa (Rate Limiting): throttle:api-movil (Máximo 100 peticiones/minuto por dispositivo: X-Device-Id + IP, o solo IP si no se envía el header)

Parámetros:

Parámetro Tipo Ubicación Requerido Descripción Ejemplo
id Entero Ruta Requerido Identificador único del edificio. /api/v1/edificios/2/accesos
solo_entradas Booleano Query Opcional Si es true, filtra y retorna únicamente accesos peatonales (ENTRADA_PRINCIPAL y ENTRADA_SECUNDARIA), descartando los vértices de geocerca perimetral (PERIMETRO). Esencial para orientar la aguja de la brújula. ?solo_entradas=true

Códigos de Respuesta:

  • 200 OK: Coordenadas recuperadas con éxito.
  • 404 Not Found: El edificio especificado no existe o está inactivo.
  • 429 Too Many Requests: Límite de peticiones excedido (más de 100 peticiones por minuto desde el mismo dispositivo).

Ejemplo de Petición para Modo Brújula (cURL):

curl -X GET "http://localhost/api/v1/edificios/2/accesos?solo_entradas=true" \
     -H "Accept: application/json" \
     -H "X-Device-Id: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"

3.8. Última Actualización del Catálogo (Verificación Ligera)

↑ Volver al índice de endpoints

Devuelve únicamente la marca de tiempo más reciente de los catálogos del campus (MAX de creado_en / actualizado_en en categorias, edificios, edificios_coordenadas_gps y etiquetas; ninguna tabla usa deleted_at). Permite saber si hay que descargar datos sin transferir el payload de edificios.

  • Método: GET Verificación / Check Ligero
  • Ruta: /api/v1/ultima_actualizacion
  • Autenticación: Pública (sin login ni tokens)
  • Protección de Tasa (Rate Limiting): throttle:api-movil (Máximo 100 peticiones/minuto por dispositivo: X-Device-Id + IP, o solo IP si no se envía el header)
  • Propósito: Verificación ligera de versión previa a la descarga completa.
  • Parámetros de Entrada: Ninguno

Flujo recomendado en la app móvil:

  1. La app consulta /api/v1/ultima_actualizacion.
  2. Si data es igual a la marca de tiempo almacenada localmente (SharedPreferences / DataStore / SQLite), omite la descarga y conserva los datos locales.
  3. Si data es más reciente, consume /api/v1/sincronizar_v2 o /api/v1/sincronizar y actualiza la marca local.

Ahorro de datos y batería: esta respuesta pesa unos pocos bytes, frente al catálogo completo de edificios. Consultarla antes de descargar evita transferencias y procesamiento innecesarios en el dispositivo.

Códigos de Respuesta:

  • 200 OK: Operación exitosa (data puede ser null si no existen registros).
  • 429 Too Many Requests: Límite de peticiones excedido (más de 100 peticiones por minuto desde el mismo dispositivo).
  • 500 Internal Server Error: Fallo al consultar la fecha; data viaja como null.

Ejemplo de Petición (cURL):

     -H "Accept: application/json" \
     -H "X-Device-Id: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d"

4. Guía de Georreferenciación y Navegación Móvil

Para asegurar una experiencia de navegación fluida y precisa, las aplicaciones consumidoras deben implementar los siguientes algoritmos basados en los datos provistos por la API:

4.1. Fórmula del Semiverseno (Haversine Distance)

Para consultar la deducción matemática y la explicación de la fórmula del semiverseno (Haversine), puedes revisar los siguientes enlaces:

  • Fórmula del haversine (Wikipedia en español)
  • Calculadora y explicación de distancia con fórmula de Haversine (PLANETCALC en español)
  • Fórmula de Haversine para encontrar la distancia entre dos puntos (GeeksforGeeks en español)

4.2. Cálculo del Rumbo / Azimut (Bearing) para Modo Brújula

Para orientar la aguja de la brújula hacia la entrada principal (ENTRADA_PRINCIPAL donde es_principal = true):

$$y = \sin(\Delta\text{lon}) \cdot \cos(\text{lat}_2)$$ $$x = \cos(\text{lat}_1) \cdot \sin(\text{lat}_2) - \sin(\text{lat}_1) \cdot \cos(\text{lat}_2) \cdot \cos(\Delta\text{lon})$$ $$\theta = \text{atan2}(y, x)$$ $$\text{rumbo en grados} = (\theta \cdot 180 / \pi + 360) \pmod{360}$$

4.3. Geocercado Pasivo (Detección de Arribo)

Cada edificio define su propio radio_cobertura (por defecto $20$ metros). Cuando la distancia $d$ calculada mediante Haversine sea menor o igual al radio: $$d \le \text{radio_cobertura}$$ La aplicación debe activar el estado de "Ha llegado a su destino" y desplegar de manera reactiva la ficha informativa con los servicios y dependencias del inmueble.

5. Ejemplos de Implementación en Clientes Móviles

5.1. Implementación en Flutter / Dart (Consumo de Sincronización)

import 'dart:convert';
import 'package:http/http.dart' as http;

Future<void> sincronizarCatalogo(String baseUrl) async {
  final url = Uri.parse('$baseUrl/api/v1/sincronizar');
  final response = await http.get(url, headers: {
    'Accept': 'application/json',
  });

  if (response.statusCode == 200) {
    final Map<String, dynamic> jsonResponse = jsonDecode(response.body);
    if (jsonResponse['success'] == true) {
      final List<dynamic> edificios = jsonResponse['data'];
      // Insertar en base de datos local SQLite (sqflite)
      for (var edif in edificios) {
        await guardarEdificioEnSqlite(edif);
      }
      print('Sincronización completada: ${edificios.length} inmuebles guardados.');
    }
  } else {
    throw Exception('Error al sincronizar catálogo: ${response.statusCode}');
  }
}

6. Almacenamiento Local Sugerido (SQLite y Alternativas Clave-Valor)

Importante: los endpoints que consume la aplicación móvil no exigen el uso de SQLite en el dispositivo. El almacenamiento local es una sugerencia arquitectónica opcional: cada desarrollador o plataforma puede elegir el medio que mejor se adapte (relacional o clave-valor ligero).

6.1. Opción A: SQLite (relacional, opcional)

Si se opta por una base de datos relacional, para almacenar los datos descargados en /api/v1/sincronizar se sugiere estructurar la base de datos local SQLite de la siguiente forma. Esta propuesta es solo una alternativa de persistencia, no un requisito para consumir el API.

8. Seguridad y Cuotas de Petición (Rate Limiting)

Para garantizar la estabilidad, alta disponibilidad y protección contra abusos de denegación de servicio (DoS) o sobrecargas accidentales, la API móvil v1 implementa un esquema nativo de limitación de tasa (Rate Limiting) configurable y de alto rendimiento.

8.1. Mecanismo en Memoria / Caché

  • Operación 100% en memoria y caché: El control de peticiones se gestiona de manera transparente a través del componente nativo RateLimiter de Laravel 12 integrado en el ciclo de vida de la aplicación (bootstrap/app.php).
  • Cero impacto en base de datos: El conteo de accesos y decaimiento de ventanas no ejecuta sentencias transaccionales sobre las tablas de MySQL de la aplicación, preservando la capacidad operativa de los inmuebles, dependencias y accesos universitarios.
  • Resolución inteligente de clientes (esquema híbrido): Si la petición incluye el encabezado X-Device-Id, el discriminador de cuota es X-Device-Id concatenado con la IP ($deviceId . '|' . $request->ip()). Si no lo incluye, se usa únicamente la IP ($request->ip()). El header es opcional pero altamente recomendado en las prácticas de clase, para que los compañeros de aula (misma IP bajo NAT) no compartan cuota.

8.2. Cuotas Establecidas

Canal / Endpoint Limitador Asignado Middleware Cuota Máxima Clave de Aislamiento Propósito / Justificación
Todos los endpoints (/sincronizar, /sincronizar_v2, /ultima_actualizacion, /edificios, /edificios/{id}, /edificios/{id}/accesos, /categorias, /etiquetas) api-movil throttle:api-movil 100 req / min por dispositivo X-Device-Id + IP (o solo IP si no se envía el header) Cuota unificada de consulta pública, pensada para soportar holgadamente las pruebas de un grupo de aula (~20 alumnos) sin que compartan cuota entre compañeros.

8.3. Cabeceras HTTP de Control y Códigos de Estado

Cuando una solicitud es procesada por el middleware de limitación, el servidor adjunta automáticamente los siguientes encabezados HTTP de respuesta:

  • X-RateLimit-Limit: Cantidad total de peticiones permitidas en la ventana (100 por dispositivo).
  • X-RateLimit-Remaining: Peticiones que le restan al cliente dentro de la ventana del minuto actual.
  • Retry-After: Cantidad de segundos que el cliente debe esperar antes de reintentar si excedió el umbral (HTTP 429).

En caso de superar el umbral máximo permitido, la API devuelve el código de estado HTTP 429 Too Many Requests con un cuerpo JSON normalizado bajo el estándar del proyecto:

{
  "success": false,
  "data": null,
  "message": "Límite de peticiones excedido (100 por minuto). Intente nuevamente en un minuto."
}

8.4. Recomendaciones de Integración para el Cliente Móvil

Para maximizar la resiliencia de la aplicación móvil ante bloqueos por cuota:

  1. Interceptor HTTP (OkHttp / Retrofit / Axios): Configurar un interceptor centralizado que detecte códigos 429 Too Many Requests.
  2. Uso de Datos Locales Embebidos (Offline-First): Si cualquier endpoint responde con 429, la aplicación no debe interrumpir la navegación ni bloquear al usuario; en su lugar, debe recurrir inmediatamente al catálogo previamente almacenado en el dispositivo (SQLite o almacenamiento clave-valor).
  3. Notificación Amigable: Informar al usuario mediante un mensaje sutil (Snackbar / Toast): "Sincronización pausada temporalmente. Usando datos guardados en el dispositivo."
  4. Respeto del encabezado Retry-After: El cliente debe posponer nuevos intentos de sincronización en segundo plano durante el lapso de segundos indicado en dicha cabecera.
  5. Envío del UUID del Dispositivo (recomendado): Incluir en cada petición la cabecera X-Device-Id con un UUID generado durante la primera ejecución de la app y guardado localmente (SharedPreferences, DataStore o UserDefaults). En las prácticas de clase evita que los compañeros compartan cuota.
